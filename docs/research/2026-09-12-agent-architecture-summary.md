# Agent 架构与 LangGraph：决策摘要

**建议采用 LangGraph JS，范围限定为 Agent 工作流；保留本机会话服务、SQLite、领域校验、采集与生成隔离。先做独立个人推演图，再将实时理解迁成有界小图。** 这是研究建议，尚未采用或实现。[详细依据与设计](2026-09-12-agent-architecture-report.md)

当前核心已有可靠性基础，不能简单评价成“一次调用、不够 Agent”。它会选择上下文、维护对象与条件、传播修订影响，并独立生成和验证表达。但它还不能主动调用历史检索工具；个人提问仍占用会议理解队列；语义提案缺少完整的服务端 ID／read set／持久批次协议；渲染失败没有形成定向修复闭环。更关键的是，真实模型理解自然讨论的效果尚未验收。

## 最值得做的改进

| 顺序 | 改进 | 用户能观察到的价值 |
|---|---|---|
| 1 | 建立语义标注、轨迹与失败分层评估 | 能知道错在听写、找证据、理解还是画图，改动有依据 |
| 2 | 服务端 ID、完整读版本、持久提案与任务 | 修订同一对象，恢复不重复应用；为并发推演提供可靠边界 |
| 3 | LangGraph 独立个人推演＋受控检索／计算 | 提问时会议继续理解；先查原话，再比较或试算 |
| 4 | 主动回查证据＋低打扰澄清 | 含糊指代先查历史，仍无法判断才提出一个具体问题 |
| 5 | 表达错误反馈与一次定向修复 | 图表有问题时保留旧版，并针对具体问题修复 |

实时转写适配与双端音源验收应另设实验。仅换 LangGraph 不会消除约 5 秒切片等待，也不会补出可靠说话人身份。

## 为什么推荐局部引入

LangGraph 可把检索、判断、工具、校验、修复、等待用户等分支显式化，也有利于团队持续接手。团队可能更熟悉它是有效因素；但需通过一次实际维护演练确认，不能把“熟悉教程”当作恢复与并发能力。官方把 LangGraph 定位为编排运行时，而不是事实数据库或自动提升智能的机制。[官方定位](https://docs.langchain.com/oss/javascript/langgraph/overview)

实时主链正常一次理解调用，证据回查或修复至多再一次；复杂推演单独运行，独立预算和持久恢复。不要用一个整场会议的 `interrupt()` 等用户答复；待澄清问题保存在业务库，后续发言继续处理。checkpoint 不等于业务命令幂等，重放仍可能再次调用模型或工具。[恢复语义](https://docs.langchain.com/oss/javascript/langgraph/checkpointers)

参考文档最值得吸收的是 ID、ensure、提案／命令分离、CAS、持久任务与真实语义评估。预算固定模板、主持人发布、Zoom 共享后端和旧赛程不适用于当前产品。生成式 UI 应保留 Agent 的组合自由，增加可信数据绑定与稳定身份。

## 目前能下的结论

静态核对确认：当前 HEAD 为 `a7d5771`，可靠性报告记录的 62 个文件指纹全部匹配；58 项单元／10 项 Electron 合成检查为已有记录，本轮没有重跑。真实语义、多人中英转写、线上耳机双音源、实际时延费用和 Windows 真机仍未验收。
