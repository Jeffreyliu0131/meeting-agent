## 每轮怎样维护

1. **开始**：实质修改前建立 `YYYY-MM-DD-主题.md`，同日重名加短后缀。沿用同一任务可续写原记录。写清目标、授权范围、接手基线、已有改动和本轮文件范围，在本索引及状态页登记。可用 [模板](template.md)，删除不适用的说明，不能保留占位答案。
2. **过程中**：重要决定、代码／文档里程碑、验证、阻塞发生后及时更新。记录实际改变和证据，不写逐步工具流水账。获授权的方向变更同时修产品／决策／专项规范，不能只藏在 session 中。
3. **交接或结束**：写清本轮完成／部分完成／阻塞、实际检查及对应版本、未验证、下一步和重入位置。更新索引与状态页；旧进行中工作不得无依据消失。记录中注明是否提交／推送，仅按实际结果填写。
4. **复核**：重读共享文件，保留其他任务新内容；执行文档检查并按实际改动完成必要产品检查。最终答复链接到记录即可，不用复述所有材料。

只读咨询不自动写文件；简单无变化答疑无需日志。用户要求沉淀认知、更新项目或继续实现时，这些记录属于授权范围内的必要维护。意外中断可能留下不完整记录，下一 session 必须核对文件与 Git，不能假设完成。

## 每轮必须记录 Windows 与 macOS

按 [双平台完成条件](../../AGENTS.md#双平台同步开发与交付每轮必做) 执行。每次开发／修复／迭代都同步两端；开始登记两端影响，结束按 [模板](template.md) 分别记录实现、包与源码基线、实际验证及缺口。不能以 Electron 共用源码或一端打包通过，省略另一端本地包更新及验证状态。

任一端实现或包未同步，记录部分完成／阻塞与下一步；两端包同步但 Windows 真机未测时，明确写运行待验。纯文档变更也填写两端不适用及原因。此要求适用于新建记录和续写中的任务，不要求改写历史验证结论。

## 什么变化需要更新哪里

| 变化 | 必须同步 |
|---|---|
| 目标、范围、用户确认改变 | `product-definition.md`、`decisions.md` 与受影响专项规范，写明替代关系 |
| 启动、UI、语言、交互改变 | `meeting-entry-spec.md`、`frontend-spec.md`、`language-spec.md`、相关契约与验收条款 |
| Agent、音源、存储、接口、隔离改变 | 技术设计／契约／相关 ADR、源码目录说明；目标与当前实现有差异时明确标注 |
| 命令、依赖、环境变量、运行方式改变 | 仓库 README、相关目录 README、配置示例；不记录凭证 |
| 测试或验收改变 | `tests/results/` 对应结果、适用代码版本／工作树范围；标准与结果分开 |
| 新文档／新目录 | 对应导航增加入口，说明职责、权威和适用范围 |
| 任何实质迭代的进度改变 | 本 session、本索引和 `status.md`；其余无关正文不重复改日期 |

## 多任务与证据规则

- 状态页容纳多个进行中任务；每个 session 有自己的文件。修改共享状态前重读，只合并自己负责的行，避免整页覆盖。
- 观察其他任务时标明“观察记录”，给出时间、来源与未核实项；不得假写其测试、用户确认或完成结果。原任务或接手者核实后可补齐，不需要另造重复日志。
- 有工具时可按记录中的任务 ID 查看历史，但这些 ID 只是辅助定位；记录本身必须足够独立，让没有原聊天的 Agent 也能接续。
- 历史授权注明范围已结束；不在 AGENTS.md 长期保留“本次允许推送”。没有相应当前授权不能做外部操作。
- 测试结果必须注明日期、命令、环境、代码基线及未提交范围。源码后来变化则需重新验证相关部分，不能继承旧的通过标记。
- 文档静态检查仅核对结构与路由；“有链接”不保证正文语义正确，收尾仍需人工式核对当前／历史、目标／实现、通过／未测的边界。
