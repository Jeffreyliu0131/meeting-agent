# 会议表达语言与Agent判断规则

> 文件职责：产品／工程设计要求，不是完成清单。当前进度与最新修订见[状态页](status.md)；已交付首版取舍见[ADR-003](adr/003-cross-platform-first-version.md)，实际结果见[验证记录](../tests/results/README.md)。具体实现以代码核对，未实现的要求仍是目标。
状态：用户已认可表达目标与判断逻辑；下面的具体协议、数值限制和执行方法是工程设计建议。关联[产品定义](product-definition.md)、[运行环境](rendering-runtime.md)。

## 1. 五类问题与表达

| 能力ID | 用户问题 | 可生成表达 | 核心操作 |
|---|---|---|---|
| E1 焦点 | 现在重点是什么？ | 短标题、关键变化、未决事项；没有结构时只用简短文字 | 展开依据、跳转原话 |
| E2 关系 | 这些事情怎样关联？ | 分组、节点、带语义连线；结构图、依赖图、论点关系 | 展开分支、查看关系依据、纠错 |
| E3 比较 | 几个方案差在哪？ | 依讨论维度生成的对照、共同约束、差异、未知项 | 选择对象、查看条件、保留比较 |
| E4 执行 | 怎样拆解、何时完成？ | 目标树、步骤、任务依赖、责任、时间安排 | 调整假设、查看影响、确认范围 |
| E5 推演 | 条件改变会怎样？ | 参数控件、前后差异、计算结果、影响图 | 试算、重算、还原、保存个人方案 |

这是一套可组合的表达能力，不是五个固定模板或固定页面。Agent决定对象数量、分组、连线、比较维度、布局意图、组合顺序和是否需要控件；应用负责正确承接。

## 2. 表达的基础语言

- 文字：标题、短断言、条件、未知、来源引用、必要注释。
- 结构：节点、容器／分组、语义连线、层级、并排关系。
- 数据：有单位的值、表格行列、系列、坐标轴、区间；没有实际数值不造量化图。
- 时间：已知日期、相对日期、持续时间、前置条件；未知端点留空。
- 交互：查看来源、展开、选择、输入参数、请求比较、请求试算、请求纠正；业务采纳由可信应用控制。
- 组合：Agent可为一个问题组合短说明＋关系图＋对照表＋条件控件；无需每次包含全部元素。

基础图元与样式规范不预设会议结论。图形语法不够时允许生成SVG；需要组合交互时允许提出HTML产物，经过运行环境校验后显示。

## 3. 语义规范

连线必须区分`depends_on`（执行依赖）、`supports`（支持）、`challenges`（质疑）、`conditions`（成立条件）、`part_of`（组成）、`alternative_to`（备选）、`supersedes`（修正取代）。每条推断关系附Agent来源类型和依据；不把相关画成因果。

讨论发生时间与工作计划时间使用不同字段和轴。日期需保留会议时区、相对表达的参照日、工作日／自然日口径和确定性；缺工期不能算关键路径。暂不提供未知地区的节假日推断。

分歧、条件支持与修正独立保存。多次提及不等于多票；没有评价依据不自动给方案打分、百分比成功率或“团队推荐”。

比较维度来自发言、用户请求或明确标记的Agent建议。不编造共同量纲；成本、风险、体验等无法直接相加时保持并列解释。

## 4. 信息密度与视觉规范

用户确认的是“短、清楚、工作级”；不是绝对删除所有说明。若删去条件会改变意思，应保留条件并收起次要细节。

初始设计参数（待可用性测试，不是效果事实）：

- 速览默认一个焦点、最多三条重要变化；更多内容进入工作区。
- 一块产物回答一个主要问题。首屏优先一个主产物，可有少量辅助；旧话题可回看，不永久堆叠所有产物。
- 短标题与短节点标签；正文过长时改用分组／展开，不机械截断关键限定词。
- 图中文字在目标尺寸可读；不通过缩小成微型文字容纳全场内容。空间不足时拆分或导航到子图。
- 来源、状态、单位不能只靠颜色表示；正文、图形、控件具有键盘或点击等价入口。
- 不出现文字溢出、节点遮挡、含义不明连线、无单位坐标轴。日期图不混淆持续时间与截止日。
- 不为“让用户看到AI在工作”添加循环动画、每句话新图或重复说明。

外观统一使用[collaborative-light-v2](design/tokens.json)，原话与产物语言遵守[语言规范](language-spec.md)。Agent自由组织内容，不自由更换应用视觉系统；正文和图形不使用玻璃材质。中英切换不得通过缩小字号容纳更长内容。

## 5. 何时生成，何时保持安静

每批新内容依次判断：

1. **理解变化**：重复／补充／纠正／新问题／条件改变／确认／无法判断。
2. **对象关联**：定位已有话题、主张、方案、关系；不能把相同内容反复新建，也不能强并独立观点。
3. **工作价值**：这次变化是否影响用户理解或行动？若只是复述，更新来源即可。
4. **表达选择**：现有产物能否补充？只有新结构明显更适合时才提出重组或新产物。
5. **交互需要**：是否存在可改变的条件、可比较对象或需要追溯的问题？没有必要就不加控件。
6. **更新时机**：默认局部自动更新；文字选择只保护对应块，历史查看和个人草稿保留版本，普通阅读不需要点按钮才能看见变化。
7. **交付校验**：事实来源、语义、结构、可渲染、可读、交互绑定都通过才替换可见产物。

输出动作：`no_change | patch_artifact | create_artifact | propose_restructure | request_clarification`。`no_change`不等于丢弃输入；转写和处理水位仍更新。

## 6. 增量原则

产物有稳定ID，对应明确问题与一组会议对象；其图形节点也能映射业务对象。修改文字、日期或条件不自动改变产物ID。形式切换可以产生新revision，保留旧版与选择依据。

同一问题的候选表达需要关联原产物；生成任务完成时检查依赖版本和generation。不能把过期画面当最新，也不能让新图覆盖用户正在操作的试算。

后台先提交会议理解，再独立准备表达。表达错误不能阻断后续发言；保持最后一个可用版本，显示“理解已更新，表达更新失败／待查看”。

## 7. Agent设计契约

Agent输出`ExpressionPlan`应包含：主要用户问题、关联对象、选择的载体、结构与布局意图、内容状态、来源、需要的操作、更新动作和简短内部选择理由。理由用于诊断，不默认展示成大段解释；不记录隐藏推理。

表达生成器据此输出`ArtifactRevision`，校验器给可操作的错误，例如“节点标题遮挡”“比较值无单位”“引用对象已被修正”。最多一次有针对性的自动修复；仍失败保留旧版，并允许手动重试。

选择载体的建议次序：最短且足够表达的文字／表格 → 关系或图表描述 → 特殊SVG → 确有组合交互需求的HTML。这个次序不是强制模板：不能因开发方便，把适合交互的工作内容永远退回静态图片。

## 8. 合成讨论的用途

[三个样例](../tests/fixtures/README.md)分别覆盖观点分歧、执行安排和条件推演：开发前用于核对契约，开发后用于测试Agent生成与修订。它们不是只能支持的三种业务，也不是把三段话映射到三份预写图。

验收允许不同有效图形；必须检查实际语义、来源和更新结果。变换措辞、顺序和条件，防止只对固定脚本有效。泛化和真实效果仍须额外测试。


## 事实与表达的可靠性约束

按[可靠性规范](agent-reliability.md)，表达读取当前范围内的对象与证据。conditional／committed 是原话含义，不授予会议确认。已改变的依赖需核对；无法确定新结论时保留待核对。正文之外的条件依据由可信 UI 呈现，不能因模型省略一个条件就解除它。结束核对汇总已有状态，不取消 Agent 自主生成表达的职责。
